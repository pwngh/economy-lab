# Balance holds: rules and enforcement

This API tracks one seller's earned CREDIT. Pending earnings are still waiting to mature. Available earnings have finished that wait and are not held. Reserved earnings sit in balance holds. Their sum is the total. An accepted payout leaves this total for the existing payout process; its payout reserve is counted separately. Debt and payout-policy checks can still refuse a request.

**The balances add up.** `pending + available + reserved = total`. Placing a hold moves an equal amount from `earned` to the hold's reserved account; releasing it reverses that move. The ledger rejects unbalanced entries and negative user balances. Reads also compare stored balances with sums rebuilt from entries. A separate status flag cannot change the amount held.

**Only available funds can be held or paid out.** These checks happen inside the transaction. Replaying the history assigns hold and payout debits to earnings that have matured, preserving funds that are still pending even when newer earnings clear sooner. Released funds become available without another wait. Returned payout credits wait the default period again, whether returned manually or after the worker gives up. Historical payouts without the new eligibility timestamp keep their previous allocation rule.

**Competing requests cannot spend the same funds twice.** Hold changes and payout requests lock the same earned account before checking funds. Holds then lock their reserved account in a fixed order. Balance reads take the earned-account lock too. The SQL race test makes two payout transactions overlap before either takes the lock, then checks that exactly one succeeds.

**A retry moves money once.** The opening conditions are stored in a ledger entry whose hash is verified. Stable transaction IDs identify each hold and release request. Under the account locks, a matching retry returns its original receipt; changed business inputs are refused. The supplied time may change on a retry. Hold IDs cannot be reused for a new hold, and release keys are scoped to the user across holds. A partial release cannot exceed the remainder. Payouts use the existing transactional idempotency check.

**Time makes a release eligible; a call performs it.** A matching event or `now >= expiresAt` allows release. `read()` changes nothing. The host calls `expire()` to release due remainders, each in its own transaction, and can retry an interrupted call. Tests advance the supplied time without sleeping. The host must authorize callers, verify events, and supply a consistent clock and policy.

**What the tests cover.** Shared examples, generated operation sequences, independent balance calculations, ledger replay, retries, and payout races run on memory, PostgreSQL, MySQL, and HTTP. The generated cases are a finite, repeatable sample. Complete history must remain in active storage; recorded archival or missing opening evidence causes an error. This pass adds no indexed hold lookup, automatic database upgrade, external payment execution, conversion, fees, or UI/API endpoints. Reads scan history and account names, so throughput at large account sizes is not established.
