# Balance holds: invariants and enforcement

The balance API manages one seller's earned CREDIT. Available means matured funds that are not held. Pending is the remainder of unheld earnings. Reserved is the sum of balance holds. Total is earnings plus holds; an accepted payout leaves this total and enters the existing payout saga. Existing accrual-debt and payout-policy checks remain additional gates; they do not change these ledger-derived buckets.

**Conservation.** `pending + available + reserved = total`. Placing a hold debits earned and credits its reserved account by the same amount. A release reverses that movement. The ledger rejects unbalanced postings and negative user balances. Reads compare cached balances with sums derived from entries, so a status flag cannot invent or erase money.

**Eligibility.** A hold can reserve only available funds. A payout still runs through `economy.submit(requestPayout(...))`, which checks earnings, maturity, and accrual debt inside its transaction. New hold and payout debits consume matured earned lots when history is replayed; this preserves older pending lots even when a newer funding source has a shorter wait. A release returns already matured credit without starting another settlement wait. Historical payouts without the new eligibility timestamp retain their prior allocation meaning.

**Serialization.** Hold mutations lock the owner's earned account and the hold account in a fixed order. Existing payout requests lock that same earned account before their balance check. A competing transaction sees either the committed movement or the preceding state under its lock; it cannot authorize a second draw from the same available amount. Snapshot reads also acquire the earned lock. The shared SQL test uses a barrier before lock acquisition to prove two transactions actually overlap and asserts exactly one payout succeeds.

**Retry safety.** Opening conditions live in an immutable, hash-verified posting. Deterministic transaction IDs identify a hold and each release request. Under the same account locks, a matching retry returns the original receipt; changed content is refused. Partial releases debit only the current remainder. Payout retries use the existing transactional idempotency claim and return the accepted transaction.

**Time and events.** The caller passes `now`. Release requires either the configured event or `now >= expiresAt`; the expiry sweep releases remaining funds and can be retried. A due timestamp is eligibility, not an automatic mutation. Tests advance values without sleeping. The host is responsible for authentic events, clock consistency, authorization, and scheduling.

**Evidence and limits.** Shared examples, seeded state-machine programs with an independent model, ledger replay, retry tests, and payout races run on memory, PostgreSQL, MySQL, and the HTTP store adapter. Missing opening evidence is refused. Full hot history is required; archival-aware holds, indexing, external payment execution, currency conversion, fees, and UI/API endpoints are not included. Reads favor a straightforward history scan over throughput. Generated programs test a finite reproducible sample, not every possible program or administrative mutation.
