Credit maturity is a waiting period before funds can be used. The wait depends on the funding source and the host's configuration. A credit is **matured** when its arrival time plus that wait is no later than the time being checked.

This is an availability rule. A payment can still be reversed after the wait ends; maturity does not remove that risk.

## When the clock starts

Each incoming credit creates a dated **lot**: an amount, an arrival time, and a funding source. The source selects a wait through `maturityHorizonMs`. If no wait is configured for that source, lookup falls back to `default`, then `card`, then `0`.

The clock starts when the credit reaches the account being read. With the [accrual split](/economy/concepts/accrual-split/), a sale first places the seller's share in a settlement account. The later drain posts it to `earned`, and the earned lot's wait starts at that posting.

The environment loader defaults an omitted card wait to `0` outside production and requires it in production. Other omitted waits inherit the card value in either environment. The quickstart therefore has no wait unless one is configured. See [maturity configuration](/economy/reference/configuration/#maturity-horizons).

## Spendable wallets: oldest funds are used first

Wallet spending uses the oldest credits first. The remaining balance therefore comes from the newest lots, sometimes called the **FIFO tail**. If a spend uses only part of a lot, its remainder keeps the original arrival time. The ledger does not rewrite the lot; reads work out the remainder from the recorded amounts.

## Seller earnings: preserve funds that are still waiting

A payout or a balance hold may use only matured earnings. That needs a different calculation from wallet spending: the oldest earned lot might still be waiting while a newer one is already available.

Earned-account reads replay the ledger history in order. New payouts and holds use eligible lots and leave pending lots alone. Historical payouts without the eligibility timestamp keep their earlier oldest-first allocation. A released hold returns money that had already matured, so the release does not start another waiting period.

For example, suppose a seller has 400 minor units still waiting and 600 available:

| Action | Pending | Available | Reserved | Total |
| --- | ---: | ---: | ---: | ---: |
| Starting balance | 400 | 600 | 0 | 1,000 |
| Place a hold for 500 | 400 | 100 | 500 | 1,000 |
| Accept a payout of 100 | 400 | 0 | 500 | 900 |
| Release 200 from the hold | 400 | 200 | 300 | 900 |

The pending 400 stays untouched throughout. The payout leaves this total because it has moved into the separate payout workflow. If that payout is later reversed or the worker gives up on it, the returned credits start the wait for an untagged funding source (normally `default`) again. With a nonzero wait they return as pending, unlike a hold release.

## Balance holds

<ApiLink to="functions/economy-lab.createBalanceHolds" /> reports four amounts for a seller:

- **Pending:** earned credits whose waiting period has not ended.
- **Available:** matured earnings that are not in a balance hold. Payout policy can still reject a request, for example because of debt or a minimum amount.
- **Reserved:** earnings moved into balance-hold accounts.
- **Total:** the sum of pending, available, and reserved.

A balance hold is a ledger transfer, not a pause flag. Placing one moves available credit from `earned` to a reserved account. Releasing it moves credit back. A hold needs an expiry time, a release event, or both. Either a matching event or a reached deadline permits a release. Supply `amount` to release part of the hold; omit it to return the remainder.

Passing the deadline does not move the money by itself. The host calls `expire({ userId, now })` from its scheduler to release due holds. Times are explicit epoch milliseconds. A read checks eligibility at `now` against the current ledger; it is not a snapshot of an earlier balance. The host supplies a consistent clock, authorizes callers, and verifies events.

Retry an opening with the same `userId` and `holdId`. Retry a release with the same `userId` and `idempotencyKey`. Matching retries return the original receipt, while changed business inputs are refused. Each new hold needs a new ID, including after an earlier hold has been fully released. Hold calls throw on invalid input or insufficient funds; payout requests instead return business declines as outcomes.

Balance holds and `PAYOUT_RESERVE` have different jobs. A hold sets earnings aside before a payout is accepted. `PAYOUT_RESERVE` contains credits already committed to the [payout workflow](/economy/concepts/payout-saga/) and is not part of the balance API's `reserved` amount.

## What a payout can use

[`requestPayout`](/economy/reference/operations/request-payout/) reads the seller's unheld `earned` balance. It then checks whether enough of that balance has matured, along with debt and other payout rules. For example:

```ts
import { requestPayout, userActor, toAmount } from '@pwngh/economy-lab';

// The account has enough earned credit, but some is still waiting.
const outcome = await economy.submit(
  requestPayout({
    idempotencyKey: 'po_2201',
    actor: userActor('usr_s1'),
    userId: 'usr_s1',
    amount: toAmount('CREDIT', 2_400_000n),
  }),
);
// An immature request returns status: 'rejected', with detail.reason: 'FUNDS_IMMATURE'.
// A rejected request can use the same key again after the waiting period ends.
```

If a hold has removed too much from `earned`, the request instead returns `INSUFFICIENT_FUNDS`. `FUNDS_IMMATURE` means the unheld balance is large enough, but not enough of it has finished waiting.

## Read cost and limits

`maturedBalance` returns the matured amount at `now`. `maturedAtLeast` answers whether that amount covers a particular request and stops adding amounts once it has enough.

For spendable wallets, both read the newest lots in pages and stop when those lots cover the live balance. Earned accounts first replay their full history, even when the requested payout is small. That makes the allocation easy to check, but the work grows with account history.

The host must keep the complete ledger history in active storage. The holds API rejects a known archive when the adapter exposes `archiveState`; the HTTP adapter does not expose that check. A missing hold opening is still refused, but these checks do not replace the host's retention responsibility.

The shared tests check earned balances against an independent model; `maturedBalanceFullScan` is the separate reference calculation for the wallet FIFO path.
