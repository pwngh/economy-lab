economy-lab is the application layer of a credits economy (wallets, a marketplace, payouts, subscriptions, and digital ownership) built as one library over a single [double-entry](/economy/concepts/accounts-and-double-entry/) ledger.

You drive it through one [`submit`](/economy/reference/the-economy/) entry point and read its state through [`read`](/economy/reference/reads/). Every action is one [`Operation`](/economy/reference/operations/) that posts a balanced transaction and returns an [`Outcome`](/economy/reference/outcomes-and-reason-codes/). The whole loop fits in a few lines:

```ts
import { createEconomy, memoryPorts, topUp, systemActor, toAmount, spendable } from '@pwngh/economy-lab';

const economy = createEconomy(memoryPorts({ signingKey: 'dev-signing-key' })); // in-memory, zero dependencies

const outcome = await economy.submit(
  topUp({
    idempotencyKey: 'ord_1001',
    actor: systemActor('billing'),
    userId: 'usr_a1',
    amount: toAmount('CREDIT', 60_000n), // the 600-credit bundle, about $5
    source: 'stripe',
  }),
);

const balance = await economy.read.balance(spendable('usr_a1'));
// outcome.status → "committed" · balance.minor → 60000n
```

Balances aren't stored and mutated. Every action becomes a balanced posting in an append-only, hash-chained ledger, and balances are folded back from those postings.

The project enforces several [invariants](/economy/concepts/the-proof/):

- value is conserved
- no account overdrafts
- every spendable credit is backed by real cash
- history can't be silently rewritten

An independent [prover](/economy/concepts/the-proof/) can re-check all of them at any moment.

## How it fits together

<SystemShape />

A `submit` is synchronous. It validates and authorizes the request first. Then it posts one balanced transaction to the [ledger](/economy/concepts/accounts-and-double-entry/), writing a matching event to an outbox in the same transaction. The [Economy API](/economy/reference/the-economy/) walks that request path step by step.

Anything that outlives a request happens off that path. A [background worker](/economy/reference/background-worker/) drains the outbox and runs the recurring sweeps: payouts, subscriptions, promos, fees, and checkpoints. The same worker runs the history-lifecycle jobs that re-prove, archive, and expire old rows.

## A lab, not a product

economy-lab is a runnable study of an application layer, shipped with a proof-carrying reference service host. Running it as a production money system is a host responsibility the docs do not yet cover: the ledger invariants are enforced to a production standard, but the operational edges are stubbed or simplified — the payout [`Processor`](/economy/ports/processor/), the FX [`Rates`](/economy/ports/rates/) source, and the regulated plumbing a money transmitter provides. The [threat model](/economy/ops/threat-model/) states exactly what the reference host enforces and what stays the host's obligation.

By default it runs entirely in memory with zero runtime dependencies. The [storage](/economy/ports/storage/) adapters run the same ledger logic on Postgres and MySQL; Redis backs the cache and the rate limiter, and the [messaging](/economy/ports/messaging/) adapter hands events to Amazon Simple Queue Service. Five conformance runners — store, cache, rate limiter, dispatcher, processor — hold each adapter to the in-memory reference. What's intentionally out of scope has its own page: [scope and non-goals](/economy/scope-and-non-goals/).

## Where the ideas come from

economy-lab invents no cryptography and no accounting. It composes four well-established ideas into one ledger:

- **Double-entry bookkeeping.** The rule that every posting balances is the method Luca Pacioli first set down in print in 1494. It's the foundation of [accounts & double-entry](/economy/concepts/accounts-and-double-entry/).
- **Hash-linked tamper-evidence.** Hashing each record onto the one before it makes any later edit detectable. The construction comes from Haber and Stornetta's [_How to Time-Stamp a Digital Document_](https://link.springer.com/content/pdf/10.1007/BF00196791.pdf) (1991), and Bitcoin would later cite it. economy-lab applies it one [hash chain](/economy/concepts/integrity/) per account.
- **Merkle trees, Certificate Transparency, and Ed25519.** The signed [checkpoint](/economy/concepts/integrity/) folds every account's head into a single Merkle root and signs it. The hash tree is Ralph Merkle's, from his [1979 thesis](https://www.ralphmerkle.com/papers/Thesis1979.pdf) and [later patent](https://patents.google.com/patent/US4881264A/). The leaf/node domain separation follows [RFC 6962](https://datatracker.ietf.org/doc/rfc6962/) (Certificate Transparency). The signature is [Ed25519](https://ed25519.cr.yp.to/) (Bernstein and colleagues).
- **Sagas.** A payout that reaches an outside rail is modeled as a long-lived transaction advanced one compensatable step at a time. That is the [saga](/economy/concepts/payout-saga/) pattern from Garcia-Molina and Salem's [_Sagas_](https://sigmodrecord.org/1987/12/09/sagas/) (SIGMOD 1987).

economy-lab binds them together (accounting conservation, cryptographic tamper-evidence, and compensatable long-lived transactions) under one [prover](/economy/concepts/the-proof/) that independently re-checks all of them.
