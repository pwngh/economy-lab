A <ApiLink to="variables/economy-lab.requestPayout" /> call reserves credits and returns a ledger outcome. The external payment finishes later, after the provider confirms it.

The stored record is a <ApiLink to="interfaces/ports.Saga" />. The [background worker](/economy/reference/background-worker/) advances it through named states, recording each completed step.<Cite n={1} /> After an interruption, the worker can read that state and retry the unfinished work.

## Why it exists

The alternative — paying synchronously inside <ApiLink to="variables/economy-lab.requestPayout" /> — couples a money posting to a network call the ledger doesn't control.

If the call hangs, the request hangs. If the process dies after the provider pays but before the ledger records it, the books and the provider disagree, with no record of why.

A long-lived record makes every intermediate state durable and named. The worker can drive a payout forward from wherever it stopped. An operator sees a stuck one rather than a silent gap.

The same shape covers anything that outlives one request. [Subscriptions](/economy/concepts/subscriptions/) reuse it to renew period after period. A promo grant expires the same way: the worker sweeps a stored row rather than holding a thread open.

## The states

`requestPayout` does not pay. It reserves the credits (`debit earned → credit payout_reserve`, two [`CREDIT` legs](/economy/concepts/accounts-and-double-entry/) that cancel out). It also opens a `Saga`: a record whose `state` walks through `SagaState` (see <SourceLink to="src/ports.ts#L1729-L1735 · SAGA_STATES" />).

The enum includes `REQUESTED`, `RESERVED`, `SUBMITTED`, `SETTLED`, and `FAILED`. Normal requests start at `RESERVED`: setting aside the credits and creating the record happen in one database transaction. A crash rolls back both or leaves both committed. The worker does not advance `REQUESTED` rows. Run the example to see the opening record:

## The two triggers

The worker's `payouts` sweep first commits `RESERVED → SUBMITTED`, then calls `processor.submitPayout` with the USD quote stored at request time. If the provider returns a reference, the worker records it. Recording `SUBMITTED` before the call matters: a lost response leaves the payment outcome unknown, so the worker cannot safely treat the reserve as unused (see <SourceLink to="src/worker/payouts.ts#L368-L389 · submitToProvider" />).

It does not settle itself. Settlement arrives on the provider's verified "payout settled" webhook. That webhook maps to a [`settlePayout`](/economy/reference/operations/settle-payout/) operation, which the worker's inbox drain applies off the request path. That operation runs the `SUBMITTED → SETTLED` step.

Failure arrives the same way, and promptly. The common real-world failure is asynchronous: the rail accepts a payout and only rejects it during processing. So a verified "payout failed" webhook maps to a [`reversePayout`](/economy/reference/operations/reverse-payout/) carrying `providerReported`. That returns the reserve as soon as the rail gives up, instead of after the timeout. When the processor adapter offers the optional `payoutStatus` probe, the sweep consults it on each look at a `SUBMITTED` saga and acts on the reported status — [the processor port](/economy/ports/processor/) walks each case. The one rule worth repeating here: a reported `SETTLED` blocks the force-fail, because a lost settlement webhook must never end in a double-pay.

## What makes it safe to re-drive

Three guards let the worker retry a step without paying twice.

- **The call to the rail is idempotent**, keyed by the saga id (`key: saga.id`), so a retried submit still pays once. The settlement webhook is deduped on the provider's event id, so a redelivered settlement settles once.
- **Each state change is a compare-and-set.**<Cite n={2} /> `sagas.advance(id, from, to, patch)` moves a saga only if it is still in `from`, and returns `false` (changing nothing) otherwise. So two sweeps racing the same saga can't both advance it. A step that re-asserts the state it is already in gets no exclusion from that predicate, because every racing sweep satisfies it; such a step passes `expectAttempts` as a second predicate, which is how the attempt counter stays exact (see <SourceLink to="src/ports.ts#L1098-L1104 · SagaStore.advance" />).
- **A stuck payout is given up on.** A submit throw the rail classified non-retryable fails the payout at once — a refusal is not an unknown outcome to wait on. Otherwise `maxPayoutAttempts` stops further hand-off retries without declaring the payment failed. An unknown outcome remains `SUBMITTED` until the timeout policy permits a return: past `maxPayoutAgeMs`, with no settlement webhook and no provider evidence that blocks the timeout. Either way the sweep flips the saga to `FAILED` and, in the same transaction, posts the exact reverse of the reservation (`debit payout_reserve → credit earned`). That returns the credits to the seller (see <SourceLink to="src/worker/payouts.ts#L114-L181 · deadLetter" />).

A payout reversal and a worker give-up return credits to `earned` with a new maturity wait
for an untagged funding source (normally `default`), measured from the return posting. If that wait is nonzero, the credits return
as pending. A [balance-hold release](/economy/concepts/credit-maturity/#balance-holds)
returns already-matured credit immediately; it does not use this payout-return policy.

Worker failure handling and `reversePayout` use the same conditional state update. A reversal posts only if the payout is still in the state it read. If the state changed first, the reversal posts nothing: the worker may have started submission, or another operation may have settled or reversed the payout. The payout may still be in progress. An operator can reverse a `RESERVED` payout before submission. A `SUBMITTED` payout can be reversed only under its provider-failure or timeout rules; a `SETTLED` payout cannot be reversed.

## The invariant

A payout moves through its states **once**, in order, no matter how many times the worker re-drives it or how its triggers race.

Every transition is a compare-and-set against the current state, so a step is applied by exactly one writer. The money posting that accompanies a transition commits in the same database transaction as the state flip, so the books and the record never diverge.

A `RESERVED` payout pays at most once, and its reserve is released exactly once: by settlement, by timeout-fail, or by an operator reversal, whichever wins the compare-and-set.

## How it's enforced

The enforcement lives in three places, and you can verify each one in the source.

- **The store's compare-and-set method.** `SagaStore.advance` is a conditional update that returns whether it changed a row, so the handler can detect and stand down on a lost race (see <SourceLink to="src/ports.ts#L1023-L1065 · SagaStore" />).
- **One transaction for each money movement.** Reservation, settlement, and reversal commit their ledger entries and state changes together. The submission step moves no money; it records `SUBMITTED` before making the external call.
- **Idempotent external calls and dedupe.** `processor.submitPayout` is keyed by the saga id (see <SourceLink to="src/ports.ts#L238-L254 · Processor" />). Inbound provider events are deduped by event id before they apply. So a redelivered webhook or a retried submit resolves to the same money move at most once.

## Operations and ports that rely on it

[`requestPayout`](/economy/reference/operations/request-payout/) opens the saga; <ApiLink to="variables/economy-lab.settlePayout" /> and <ApiLink to="variables/economy-lab.reversePayout" /> move it. The worker's `payouts` sweep and its inbox drain drive transitions off the request path. The opening transaction's `meta.sagaId` names the saga, so the requester can follow it with `read.saga(sagaId)`.

The saga records persist through the `SagaStore` sub-store of the [`Store`](/economy/ports/storage/) port, and a payout's disbursement leaves through the [`Processor`](/economy/ports/processor/) port. The discipline the saga depends on — a compare-and-set on every transition, one transaction per step — is the same machinery that keeps the [ledger's integrity invariants](/economy/concepts/integrity/) intact under concurrency.
