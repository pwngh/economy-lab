A posting either commits or it doesn't. A message has no such guarantee. It can be sent and lost, sent twice, or sent about a move that never committed.

This page covers the ports that keep the two honest with each other. The <ApiLink to="types/ports.Dispatcher" /> carries events out. The transactional outbox and inbox rows carry those events through storage. The rows themselves live on the [`Store`](/economy/ports/storage/). The patterns that use them live here.

## The `Dispatcher`: events out

The `Dispatcher` is the simplest port in the system. It is a single function that takes an <ApiLink to="interfaces/ports.EconomyEvent" /> and hands it off for delivery. The core builds the event. The adapter decides where it goes.

```ts
type Dispatcher = (event: EconomyEvent, options?: CallOptions) => Promise<void>;
```

Two adapters ship. `sqs` in `@pwngh/economy-sqs` publishes each event to an [Amazon Simple Queue Service (SQS)](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/welcome.html) queue as JSON. An HTTP dispatcher POSTs each event to a configured URL. With neither `SQS_QUEUE_URL` nor `DISPATCHER_URL` set, no dispatcher is wired. In that case the worker's relay sweep short-circuits, and outgoing events stay pending in the outbox. The `Dispatcher` is optional. The economy runs without one.

Delivery is at-least-once. SQS may deliver a message twice; every event carries its id, and the receiver drops duplicates. The outbox below uses the same pattern.

## The outbox

The `Dispatcher` alone leaves one problem unsolved. If the money commits but the event send fails, the event is lost. If you send first and the commit rolls back, you have announced a move that never happened. The fix is to make the event part of the transaction.

That's the transactional outbox.<Cite n={1} /> When a money move commits, its outgoing event is written to the `outbox` sub-store _in the same database transaction_. A separate relay ([the background worker](/economy/reference/background-worker/)) ships pending rows through the `Dispatcher`. As a result, an event is never sent for a rolled-back move, and never lost for a committed one.

The relay is `relayOutbox` in `src/worker/relay.ts`. It claims a batch of pending rows and sends each row in its own try/catch — one failure can't stop the batch. It marks the delivered rows done. The attempt is counted against the row before the send, so a send that throws is left pending having already spent one, and the next run retries it. Counting first is what covers the send that never comes back at all: a row whose every delivery kills the relay process still walks to its cap, because nothing after the send has to run for the count to be durable. Once a row hits the configured cap, the relay dead-letters<Cite n={2} /> it to a terminal `dead` state. That way one poison event can't wedge the queue behind it. A throw the dispatcher classified non-retryable dead-letters on the first delivery instead of walking to the cap. The shipped adapters wrap every transport failure retryable, so that verdict only comes from a host's own dispatcher. The bundled @pwngh/taskq bridge is one consumer on the far side. It enqueues each delivery as a durable task keyed by the event id ([the packages](/economy/ports/packages/)).

## The inbox

The `inbox` is the mirror image, for events coming _in_. A verified provider webhook is mapped to the [`Operation`](/economy/reference/the-economy/) it should apply, then saved to the `inbox` in the same transaction as the webhook ingress that claimed it. A separate apply sweep submits each pending operation and marks the row applied.

An inbound event can't be applied without first being recorded, and every recorded event is eventually applied or dead-lettered. The apply is off the request path. The webhook returns as soon as the row is safely stored, and the money moves when the worker drains it.

Webhook ingress and the provider side of all this belong to the [processor port](/economy/ports/processor/). The outbox/inbox is the storage seam those flows write through.

## What the host owns

The dispatcher adapters are economy-lab's own. The far side is the host's: it constructs the SQS client and owns the queue, its retention, and its consumers. economy-lab publishes to it only when `SQS_QUEUE_URL` selects it.

The [`@aws-sdk/client-sqs`](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/sqs/) driver is a peer dependency; the host pins the version it runs. The adapter types the client's surface structurally, so the file compiles and unit-tests without the package installed.
