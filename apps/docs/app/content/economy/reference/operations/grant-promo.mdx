<ApiLink to="variables/economy-lab.grantPromo" /> drops marketing credit into a user's [`promo`](/economy/concepts/accounts-and-double-entry/) balance with an expiry date. A campaign can hand out credit that reverts to the platform if it goes unspent.

Here a marketing service grants a user 240 credits that expire 24 hours from now:

<CallTabs name="grant-promo" http={grantPromoHttp}>

```ts
const outcome = await economy.submit(
  grantPromo({
    idempotencyKey: 'promo_2026_06_27_usr_buyer',
    actor: systemActor('marketing'),
    userId: 'usr_buyer',
    amount: credits(240),
    expiresAt: Date.now() + 86_400_000, // 24 hours
  }),
);
// → { status: "committed", transaction: { id: "txn_…", … } }
```

</CallTabs>

The grant lands immediately. Promo credit carries no maturity hold, and a buyer's `promo` balance is drawn before their own money on the next [`spend`](/economy/reference/operations/spend/).

## Parameters

The payload fields, beyond the `kind` tag, are:

| Field            | Type                                                       | Default    | Description                                                                                                                                   |
| ---------------- | ---------------------------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `idempotencyKey` | `string`                                                   | (required) | Retried submits under the same key run at most once ([idempotency](/economy/concepts/idempotency/)).                                     |
| `actor`          | [`Principal`](/economy/concepts/actors-and-authorization/) | (required) | Who is asking. Must be a `system` or `operator` principal.                                                                                    |
| `userId`         | `string`                                                   | (required) | The user whose `promo` balance the grant raises.                                                                                              |
| `amount`         | [`Amount`](/economy/concepts/money-model/)                 | (required) | How much credit to grant. Must be `CREDIT` and positive.                                                                                      |
| `expiresAt`      | `number`                                                   | (required) | When the grant expires, in epoch milliseconds. Must be a whole-millisecond timestamp strictly in the future, and no more than five years out. |

## Returns

`grantPromo` resolves to an [`Outcome`](/economy/reference/outcomes-and-reason-codes/).

- `committed`: the success status, carrying the posted `transaction`.
- `duplicate`: a repeat key returns the original transaction; no new money moves.

`grantPromo` returns no `rejected` outcome. A malformed request throws instead. See [reason codes](#reason-codes).

## Postings

The grant posts one entry with two legs. One leg raises the user's `promo` balance. The other books the offset on the platform's `PROMO_FLOAT` account.

| Account              | Side   | Amount   |
| -------------------- | ------ | -------- |
| `SYSTEM.PROMO_FLOAT` | debit  | `amount` |
| `promo(userId)`      | credit | `amount` |

`PROMO_FLOAT` is debit-normal, so debiting it raises its balance to mirror the credit added to the user's `promo` account.

<Callout type="note">
  Promo credit needs no USD backing, unlike topped-up money. A grant raises no
  obligation the platform must hold cash against, so it never increases the
  trust balance. Promo credit is spendable but never paid out. Only earned
  credit cashes out.
</Callout>

The handler also records the grant in the same unit of work, reusing the posting's id. That id is how the [expiry sweep](/economy/reference/background-worker/) later finds the grant and reverses any unspent portion.

## Authorization

`grantPromo` is privileged. Only a `system` or `operator` [`Actor`](/economy/concepts/actors-and-authorization/) may call it.

The gate refuses an end-user principal. The operation mints credit into an arbitrary user's account, so it sits in the engine's restricted-to-privileged set alongside <ApiLink to="variables/economy-lab.topUp" /> and the entitlement grants. A `user` principal raises an `AUTH.UNAUTHORIZED` fault before any work runs.

## Reason codes

`grantPromo` has no `rejected` path. It declines no well-formed request: there is no affordability check, and the pause gate never applies to privileged actors. Every failure is a thrown fault.

The faults it can throw, all from malformed input, are:

| Code                   | When                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `OP.MALFORMED`         | `amount` is not `CREDIT`, or `expiresAt` is not a whole-millisecond timestamp, is not in the future, or is more than five years out. |
| `MONEY.INVALID_AMOUNT` | `amount` is zero or negative.                                                                                                        |
| `AUTH.UNAUTHORIZED`    | The caller is a `user` principal.                                                                                                    |

<Callout type="warning">
  A zero, negative, or past `expiresAt` throws `OP.MALFORMED` on purpose. The expiry sweep
  claims any grant whose `expiresAt` has already passed, so a past timestamp
  would let the sweep claw the credit straight back.
</Callout>

## Preconditions and invariants

Every grant must expire. The five-year ceiling on `expiresAt` stops a caller from minting effectively never-expiring credit with an absurd far-future timestamp. The ceiling keeps the expiry sweep able to reclaim every grant.

The grant and its bookkeeping row commit or roll back together. The recorded grant reuses the posting's id, and the row write is idempotent on that id. So a retried grant never duplicates the row.

When a grant expires, the worker's promo sweep reverses whatever is unspent. A partly-spent grant returns only the remainder, and a fully-spent one posts nothing.

Every grant a user holds pools into the one `promo` account, so the balance alone cannot say which grant paid for a purchase. A purchase draws down the grant that expires soonest. An expiring grant therefore claws back what the pool holds above what the user's later-expiring grants still claim, never more than its own face value. Credit belonging to a grant that has not expired stays where it is.

A [refund](/economy/reference/operations/refund/) of a promo-funded purchase puts that promo credit back, and it does so whether or not the grant that paid for the purchase is still open. Credit restored above the total face value of the user's live grants belongs to no grant: no expiry can reach it, because a clawback stops at its own grant's face. The same sweep therefore takes it back to `PROMO_FLOAT`. Granted credit is the platform's marketing spend rather than money held in trust, so a grant that has already run its course does not turn into a permanent balance by way of a refund.

Both reversals mirror the original entry. They debit the user's `promo` account and credit `PROMO_FLOAT`.
