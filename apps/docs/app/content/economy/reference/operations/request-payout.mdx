<ApiLink to="variables/economy-lab.requestPayout" /> accepts a seller's request to cash out. It moves eligible earnings into the payout reserve and creates a stored [payout record](/economy/concepts/payout-saga/). A [background worker](/economy/reference/background-worker/) submits the payment later; accepting the request does not mean the payment has settled.

Here a seller asks to cash out 25,000 of their earned credits, clearing the default payout minimum. The amount draws on their own [`earned`](/economy/concepts/accounts-and-double-entry/) balance, in `CREDIT`:

<CallTabs name="request-payout" http={requestPayoutHttp}>

```ts
const outcome = await economy.submit(
  requestPayout({
    idempotencyKey: 'payout_2026_07_usr_a1',
    actor: userActor('usr_a1'),
    userId: 'usr_a1',
    amount: credits(25_000), // ≈ $125 at the payout rate
  }),
);
// → { status: "committed", transaction: { id: "txn_…", … } }
```

</CallTabs>

Retry a request with the same [`idempotencyKey`](/economy/concepts/idempotency/) and the same payload. Once the request commits, a matching retry returns its original transaction and does not reserve funds again. A business rejection rolls back the claim, so the caller can retry that key after the condition changes.

A business decline is returned as data. Check `detail.reason` to decide what to show the caller:

```ts
if (outcome.status === 'rejected') {
  if (outcome.detail.reason === 'BELOW_MINIMUM') {
    const { minimum, amount } = outcome.detail; // show the minimum and requested amount
  }
  if (outcome.detail.reason === 'PAYOUT_TOO_SOON') {
    const retryAt = outcome.detail.retryAt; // the earliest retry time based on current payout activity
  }
  if (outcome.detail.reason === 'FUNDS_IMMATURE') {
    const readyAt = outcome.detail.availableAt; // when enough unheld earnings would mature
  }
}
```

## Parameters

The payload fields, beyond the `kind` tag, are:

| Field            | Type                                                       | Default    | Description                                                                                                       |
| ---------------- | ---------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------- |
| `idempotencyKey` | `string`                                                   | (required) | A retried submit with the same key runs at most once. See [idempotency](/economy/concepts/idempotency/).          |
| `actor`          | [`Principal`](/economy/concepts/actors-and-authorization/) | (required) | Who is asking. A `user` may request only their own payout.                   |
| `userId`         | `string`                                                   | (required) | The seller whose available earnings will fund the payout. |
| `amount`         | [`Amount`](/economy/concepts/money-model/)                 | (required) | How much earned credit to set aside. Must be `CREDIT` and strictly positive. |

The request uses `CREDIT` from `earned`, not from a wallet's `spendable` or `promo` balance. If the payout settles, the stored quote determines the USD payment. If it fails and is reversed, the reserved credits return to `earned` and start the configured `default` maturity wait again. This differs from a balance-hold release, which makes its returned credits available immediately.

## Returns

`requestPayout` resolves to an [`Outcome`](/economy/reference/outcomes-and-reason-codes/).

- `committed`: a successful request. It carries the reservation transaction.
- `duplicate`: a matching retry of a committed request. It carries the original transaction.
- `rejected`: a business decline with one of the [reason codes](#reason-codes) below. No payout reservation is committed.

## Postings

The commit posts one balanced [double-entry](/economy/concepts/accounts-and-double-entry/) transaction. Both legs are `CREDIT` and cancel out. No USD moves here.

| Account                                                                 | Side   | Amount   |
| ----------------------------------------------------------------------- | ------ | -------- |
| `earned(userId)`                                                        | debit  | `amount` |
| [`SYSTEM.PAYOUT_RESERVE`](/economy/concepts/accounts-and-double-entry/) | credit | `amount` |

The credits now belong to the payout workflow. They leave the balance-holds API's `total`; they are not counted in that API's `reserved` bucket. `PAYOUT_RESERVE` and a [balance hold](/economy/concepts/credit-maturity/#balance-holds) are separate accounts with different release rules. The USD entry is posted only when the payout settles.

The same transaction creates a <ApiLink to="interfaces/ports.Saga" /> in state `RESERVED` (see <SourceLink to="src/ports.ts#L1729-L1735 · SAGA_STATES" />). It stores the USD quote and rate ID at request time. The quote uses the [`payout`](/economy/concepts/money-model/) rate and rounds down. The worker submits that stored amount, and settlement records it without looking up a new rate. A payout rate above `par` is refused with `CONFIG_INVALID`.

The committed transaction's `meta.sagaId` names the saga it opened, so a caller can follow the payout with `read.saga(sagaId)` instead of scanning `read.payouts()` for its own request.

## Authorization

`requestPayout` is not a privileged operation, so an end `user` can run it, but only for their own account. The ownership check requires the caller to own the `earned` account being debited; a `user` requesting another seller's payout is refused with `AUTH.UNAUTHORIZED` (see <SourceLink to="src/economy.ts#L948 · debitedUserAccounts" />).

A `system` service or a human `operator` may also request a payout on a seller's behalf. See [actors and authorization](/economy/concepts/actors-and-authorization/) for the full rule.

<Callout type="note">
  During a maintenance window, a `user`'s request is declined with
  `ECONOMY_PAUSED` carrying `resumesAt`; a `system` or `operator` request still
  goes through.
</Callout>

## Reason codes

Each check below returns a `rejected` [`Outcome`](/economy/reference/outcomes-and-reason-codes/) rather than throwing. The business checks run top to bottom, so the cheapest decline comes first. `ECONOMY_PAUSED` is separate. It is a maintenance gate checked up front, before any of them.

| Code                 | When                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `BELOW_MINIMUM`      | The `amount` is under `payoutMinimumEarnedMinor` (default `2_000_000` minor).                        |
| `PAYOUT_TOO_SOON`    | Less than `payoutMinIntervalMs` (default 24h) since the most recent update to any of the seller's payout records; carries `retryAt`. |
| `PAYEE_UNVERIFIED`   | A payee directory is configured and the seller's identity verification isn't `CLEARED`; carries the `userId`. |
| `INSUFFICIENT_FUNDS` | Unheld `earned` credit, after subtracting pending accrual debt, is below `amount`. |
| `FUNDS_IMMATURE`     | The unheld balance covers `amount`, but not enough of it has matured. Carries `availableAt`, assuming no further postings or policy changes. |
| `ECONOMY_PAUSED`     | A `user`'s request lands inside a maintenance window; carries `resumesAt`.                           |

The payee check only exists when the host composes a payee directory in. The economy-edge bridge supplies one backed by the payout rail's hosted identity verification ([the packages](/economy/ports/packages/)). Without a directory, the gate is absent.

A balance hold has already moved its amount out of `earned`, so held money cannot fund the payout. Pending earnings can still be present in `earned`; the [maturity check](/economy/concepts/credit-maturity/) makes sure the available portion covers the request (see <SourceLink to="src/operations/requestPayout.ts#L74-L104 · requestPayout">source</SourceLink>).

The cooldown uses the greatest `updatedAt` across the seller's payout records. Processing and settlement updates can therefore move `retryAt` later. The 24-hour default is a configurable policy, not a statement about a legal or payment-provider requirement.

<Callout type="warning">
  Enough total earnings does not mean enough available funds. Pending credits
  must finish their configured wait, and held credits must be released before
  they can fund a payout.
</Callout>

A malformed request throws instead:

| Code                   | When                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `OP.MALFORMED`         | The `amount` isn't `CREDIT`.                                                                                                |
| `MONEY.INVALID_AMOUNT` | The `amount` is zero or negative (see <SourceLink to="src/operations/requestPayout.ts#L237 · payableCredit" />).             |

Both are programming errors.

## Preconditions and invariants

The request reserves credit. It never disburses USD. After a `committed` outcome:

- The reserved `amount` has left the seller's `earned` balance and sits in `PAYOUT_RESERVE`. Both legs are `CREDIT` and sum to zero, so the books stay balanced.
- Exactly one `Saga` exists for the request, opened in `RESERVED`. The reservation and the saga commit in one transaction, so a record can't exist without its credits set aside, or the reverse.
- No real USD has moved, and the credits are not spendable. They leave `PAYOUT_RESERVE` exactly once afterward. They go to `REVENUE` on settle, or back to `earned` on a reversal or timeout (see [the payout saga](/economy/concepts/payout-saga/)).

## Caveats

- `requestPayout` never pays. It reserves credits and opens the saga. The worker's `payouts` sweep does the paying, later and off this path.
- It uses matured, unheld earnings only. `detail.availableAt` describes the maturity wait, not when a separate balance hold will be released.
- `BELOW_MINIMUM` enforces `payoutMinimumEarnedMinor`. `PAYOUT_TOO_SOON` enforces a cooldown after the seller's latest payout-record update.
- The reserve leaves `PAYOUT_RESERVE` exactly once — settle, reversal, or timeout — whatever races.
