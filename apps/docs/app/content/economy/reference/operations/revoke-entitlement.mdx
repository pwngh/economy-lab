<ApiLink to="variables/economy-lab.revokeEntitlement" /> removes a user's ownership of a SKU. It is the mirror of [`grantEntitlement`](/economy/reference/operations/grant-entitlement/). Ownership is a record, not a balance. No money moves, and the operation leaves the ledger untouched.

You name the user and the SKU, and optionally a `reason` for the audit trail:

<CallTabs name="revoke-entitlement" http={revokeEntitlementHttp}>

```ts
const outcome = await economy.submit(
  revokeEntitlement({
    idempotencyKey: 'revoke_usr_owner_wrld_pass',
    actor: systemActor('fulfillment'),
    userId: 'usr_owner',
    sku: 'wrld_pass',
    reason: 'chargeback', // optional
  }),
);
// → { status: "committed", transaction: { id: "txn_…", … } }
```

</CallTabs>

Once this commits, [`read.entitled("usr_owner", "wrld_pass")`](/economy/reference/reads/) returns `false`. Any UI that gates access on that SKU stops granting it.

The one business decline is a user who never owned the SKU:

```ts
if (outcome.status === 'rejected' && outcome.detail.reason === 'NOT_ENTITLED') {
  const { userId, sku } = outcome.detail; // which ownership check came back empty
}
```

## Parameters

The payload fields, beyond the `kind` tag, are:

| Field            | Type                                                       | Default    | Description                                                                                                                 |
| ---------------- | ---------------------------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------- |
| `idempotencyKey` | `string`                                                   | (required) | Same-key retries run at most once. See [idempotency](/economy/concepts/idempotency/).                    |
| `actor`          | [`Principal`](/economy/concepts/actors-and-authorization/) | (required) | Who is asking. Must be `system` or `operator`, see [Authorization](#authorization).                                         |
| `userId`         | `string`                                                   | (required) | The user losing ownership. A blank or whitespace-only value throws.                                                         |
| `sku`            | `string`                                                   | (required) | The item or feature code to revoke, such as `"wrld_pass"`. A blank or whitespace-only value throws.                         |
| `reason`         | `string`                                                   | —          | Optional note for the audit trail; omitted when not given.                                                                  |

## Returns

`revokeEntitlement` resolves to an [`Outcome`](/economy/reference/outcomes-and-reason-codes/).

- `committed`: the user owned the SKU and the ownership record was dropped.
- `duplicate`: a request with the same `idempotencyKey` already ran; the earlier `transaction` is returned unchanged.
- `rejected`: the user did not own the SKU. The only `RejectionCode` here is `NOT_ENTITLED`.

The `committed` [`transaction`](/economy/concepts/accounts-and-double-entry/) is a lifecycle marker. It carries a fresh id and commit time. Its `legs` and `links` lists are empty, because nothing posted to the ledger.

## Postings

None. Entitlements track ownership only, so `revokeEntitlement` writes no [double-entry posting](/economy/concepts/accounts-and-double-entry/) and touches no account.

The handler drops the ownership record through `unit.entitlements.revoke`. This is the operator door and it names no source, so it drops every grant on the SKU, whatever bought or subscribed for it. The returned `transaction` carries empty leg and link lists.

## Authorization

`revokeEntitlement` is platform-initiated only. An end user (`actor.kind === "user"`) may never run it. See [actors and authorization](/economy/concepts/actors-and-authorization/).

A revoke names an arbitrary `userId` the caller need not own. It also posts no debit the ownership check could catch. So the engine gates it up front. Only a `system` service or a human `operator` may call it.

A `user` actor is declined with an `AUTH.UNAUTHORIZED` fault before any work begins.

## Reason codes

`revokeEntitlement` returns one [`RejectionCode`](/economy/reference/outcomes-and-reason-codes/):

| Code           | When                                                                  |
| -------------- | --------------------------------------------------------------------- |
| `NOT_ENTITLED` | The user does not currently own `sku`, so there is nothing to revoke. |

The rejection carries the `userId` and `sku` in its `detail`, so the caller knows which ownership check came back empty.

A malformed request throws instead:

| Code           | When                                          |
| -------------- | --------------------------------------------- |
| `OP.MALFORMED` | A blank or whitespace-only `userId` or `sku`. |

A blank field would revoke against a phantom user or SKU, so a malformed request surfaces as a client error rather than a silent `NOT_ENTITLED`.

## Preconditions and invariants

The handler checks ownership before it revokes. It calls `entitlements.owns(userId, sku)` and returns `NOT_ENTITLED` when the user does not hold the SKU.

A retry under the same key returns the first result as `duplicate` rather than re-running.

The ledger's money invariants ([conservation, no-overdraft, and backing](/economy/concepts/integrity/)) are unaffected, because this operation moves no money.
