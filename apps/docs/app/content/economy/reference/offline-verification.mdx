## Why verification must leave the building

Everything [the proof](/economy/concepts/the-proof/) checks lives in the same database as the ledger it vouches for. That covers the per-account hash chains, the Merkle root, and the signed checkpoint. Against an outsider, that is enough. Against an insider who can rewrite that database, it is not. Whoever can edit the postings can also edit the checkpoints table sitting next to them.

Offline verification closes that gap by making the evidence portable. The economy exports its whole ledger as one file. Anyone who holds that file and the published signing public key can re-run the same provers the live system runs. They can run them on another machine, with no store credentials and no economy running. The auditor needs nothing from you but bytes.

## The export file

<SourceLink to="src/contract.ts#L734">read.export</SourceLink> streams the ledger as JSON Lines — one JSON object per line — with three line types in a fixed order:

1. **A header** declaring the format, which lets the verifier refuse random files: `{"format":"economy-lab/ledger-export","v":1}`.
2. **One line per chain link**, grouped by account in lineage order from genesis to tip. Each link carries the full posting — transaction id, legs, metadata, and both hashes — so the file alone is enough to re-derive every chain (<SourceLink to="src/economy.ts#L1664">exportLedger</SourceLink>).
3. **The latest checkpoint**, if one has been sealed: the signed Merkle root, its signature, and the [`kid`](/economy/ports/signer/) of the key that sealed it.

Two properties make the file suitable as evidence. First, money never travels as a JSON number. Legs carry the same decimal strings as every other wire surface, so amounts survive any JSON parser intact. Second, field order comes from the wire codec, never from object iteration. The same ledger therefore always exports byte-for-byte the same file.

```ts
import fs from 'node:fs/promises';

const lines: string[] = [];
for await (const line of economy.read.export()) {
  lines.push(line);
}
await fs.writeFile('ledger-export.jsonl', lines.join('\n'));
```

The export is always the whole ledger. A partial export cannot be chain-verified, because every account's chain must start at genesis for the hashes to re-derive. That is why there is no range parameter. Ranged reads belong to `read.statement`.

## Running the verifier

<SourceLink to="src/verify-export.ts#L231">verifyExport</SourceLink> on the main entry is the standalone counterpart to the live provers. It needs no store and no economy boot. The file is the only input. An auditor who holds the export and the published key needs the package, not this repository.

```ts
import { verifyExport } from '@pwngh/economy-lab';

const lines = exported.split('\n');
const report = await verifyExport(lines, [publicKeyHex]);
```

The repository wraps the same call as a command (`scripts/ledger-verify.ts`):

```
node scripts/ledger-verify.ts ledger-export.jsonl --key <hex Ed25519 public key>
make ledger-verify FILE=ledger-export.jsonl KEY=<hex Ed25519 public key>
```

Either way, the verifier rebuilds a read-only ledger view over the file and runs the production provers against it. Those are the same `proveChain` and `verifyCheckpoint` the live economy runs, not a reimplementation. The report says what was checked and what held:

```json
{
  "chainIntact": true,
  "firstBreak": null,
  "accounts": 5,
  "checkpoint": {
    "present": true,
    "signatureChecked": true,
    "id": "chk_1",
    "kid": "ba89e65bb74283d6",
    "verified": true
  }
}
```

A broken or tampered chain reports the first break: which account, which transaction, and whether the link chain snapped or a hash stopped matching. The exit code is `0` only when everything asked of the run verified. The command therefore slots straight into scripts and automated checks.

Two honesty rules govern the checkpoint half:

- **No key, no pass.** Without `--key`, the report states `signatureChecked: false`. The verifier never silently treats the signature as valid. Pass `--key` more than once to accept signatures from rotated-out keys. This mirrors how the live signer's prior keys work.
- **The checkpoint verifies against the exported tip.** A checkpoint sealed before the last postings honestly reports as unverified. The root it signed no longer matches the heads in the file. Export right after a seal for a clean pass.

The public key comes from <SourceLink to="src/runtime.ts#L195">signingPublicKeyHex</SourceLink>. Publish it wherever your auditors can find it. The checkpoint's `kid` is the first 16 hex characters of that same public key. An auditor can therefore confirm at a glance that the row was sealed by the key they hold.

## Anchoring checkpoints outside the ledger's database

Exports are pulled. Anchoring pushes. The <SourceLink to="src/ports.ts#L1477">Anchor</SourceLink> port publishes every sealed checkpoint to a store outside the ledger's database — an external log, an object store, or a transparency service. It does this because a checkpoint row kept next to the postings proves nothing against whoever controls that database.

Wire one through `Ports.anchor`. [The background worker's](/economy/reference/background-worker/) seal then publishes each checkpoint as it lands (<SourceLink to="src/worker/checkpoint.ts#L115">publishAnchor</SourceLink>). Publishing is best-effort by design, because a down anchor must degrade protection, not sealing. A failed publish logs `worker.checkpoint.anchor_failed` and counts on the meter. The seal completes regardless. The counter is the operator's signal to re-anchor by hand.

The bundled adapter is <SourceLink to="src/adapters/http-anchor.ts#L36">httpAnchor</SourceLink> on the `adapters` subpath. It POSTs the checkpoint as JSON with the checkpoint id in an `Idempotency-Key` header. A retried publish of the same row therefore dedupes at the receiver. The port is one method. If HTTP doesn't fit your log, a file appender or an object-store writer is a few lines.

Together the three pieces close the insider gap. The anchor puts the signed root beyond the database's reach, the export puts the evidence in the auditor's hands, and the verifier lets the auditor check one against the other without trusting you.

## When history has been archived

A ledger that has [archived](/economy/ops/archival/) its oldest history no longer holds every posting in hot storage. An export reflects that. The hot chains prove back to the archive boundary, and the boundary itself is signed. The signature covers per-account archive heads sealed under a Merkle sum-root, and a watermark records how far the move reached. Verification composes across the seam. The hot prefix re-derives from the export as before. The boundary's signature vouches for everything that moved, and the host can check it against the archived pages in its cold store.

The boundary is not one more claim in the report. It is where those chains start: an account the boundary names anchors its remaining links at the archived head, so a boundary that failed its signature, or one no key was supplied for, leaves `chainIntact` with nothing under it. The verifier answers `chainIntact: false` in both cases and puts a `BoundaryBreak` in `firstBreak` saying which. This is where the boundary and the checkpoint part company: leaving a checkpoint unchecked costs the checkpoint's own claim and nothing else, so `--key` is optional for it in a way it is not for an archived export.
