## The shape of an answer

Every call to `submit` resolves to one <ApiLink to="types/economy-lab.Outcome" />. The
`status` field tells you which of three things happened. The rest of the object carries exactly
what that status implies.

```ts
type Outcome =
  | { status: 'committed'; transaction: Transaction }
  | { status: 'duplicate'; transaction: Transaction }
  | { status: 'rejected'; detail: RejectionDetail };
```

A request lands one of three ways: it went through, it repeated an operation already done, or it
was valid but declined for a business reason.

### `committed`: it went through

A `committed` outcome means money moved. It carries the [`Transaction`](/economy/concepts/accounts-and-double-entry/)
that posted: its id, the time it committed, and the balanced debit and credit legs that recorded
the movement.

```ts
const result = await economy.submit(
  topUp({
    idempotencyKey: 'ord_1',
    actor: systemActor('payments'),
    userId: 'usr_buyer',
    amount: toAmount('CREDIT', 60_000n), // the 600-credit bundle
    source: 'card',
  }),
);
if (result.status === 'committed') {
  console.log(result.transaction.id); // → "txn_…"
}
```

Its `legs` are the lines that posted. Its `links` record how
each touched account's hash chain advanced. That advance is the per-account integrity trail
described under [the chain](/economy/concepts/integrity/).

### `duplicate`: you already did this

A `duplicate` outcome means you submitted an operation whose `idempotencyKey` matched one already
processed. The economy returned the earlier result instead of running it again. This is the
visible side of [idempotency](/economy/concepts/idempotency/), where a retried request runs at most once.

It carries the same <ApiLink to="interfaces/economy-lab.Transaction" /> the original commit did, so a `duplicate` counts as success.
A network retry, a double-clicked button, or an at-least-once delivery queue all land here.
The caller can treat `duplicate` exactly like `committed`.

<Callout type="tip">
  If you only care whether the money moved, branch on `committed` and
  `duplicate` together. Both hand you the same `transaction`. Reserve a
  separate path for `rejected`.
</Callout>

### `rejected`: a declined-but-valid request

A `rejected` outcome means the request was well-formed and the system was healthy, but the answer is
no. It carries a <ApiLink to="types/economy-lab.RejectionDetail" /> in `detail`. That object is a discriminated union: `detail.reason` names
the [`RejectionCode`](#the-rejectioncode-catalog), and the remaining fields carry exactly the
specifics that decline needs. Those specifics might be the account that was short, the order that
wasn't found, or when writes resume.

```ts
const result = await economy.submit(
  spend({
    idempotencyKey: 'idem_0',
    actor: userActor('usr_buyer'),
    orderId: 'ord_1',
    buyerId: 'usr_buyer',
    sku: 'wrld_pass',
    price: toAmount('CREDIT', 48_000n), // a 480-credit listing
    recipients: [{ sellerId: 'usr_seller', shareBps: 10_000 }],
  }),
);
if (result.status === 'rejected' && result.detail.reason === 'INSUFFICIENT_FUNDS') {
  // show the buyer a "not enough funds" message
}
```

A rejection comes back as data — you handle it in an ordinary `if` branch. See the [throw-versus-decline rule](#rejected-versus-thrown) below.

The money fields in `detail` — `need`, `have`, `minimum`, `amount` — are branded [`Amount`](/economy/concepts/money-model/)s. A caller compares them directly (`detail.have.minor < detail.need.minor`) and formats them with <ApiLink to="functions/economy-lab.encodeAmount" />. Over the [HTTP service](/economy/reference/http-service/) a rejection travels as `{ status, reason, detail }`. The top-level `reason` is a convenience copy derived from `detail.reason`. In TypeScript, `detail.reason` is the sole discriminant. The money fields travel as the same decimal strings every other wire amount uses. `bigint` fields such as `limitMinor` become decimal strings too.

## The `RejectionCode` catalog

A <ApiLink to="types/economy-lab.RejectionCode" /> names one expected reason a valid request gets declined on a healthy system. Each
one is a stable string you can branch on. Each is raised by a specific set of operations.

The table lists every code, what it means, and which operation kinds return it. The operation names
map to the pages under [operations](/economy/reference/operations/).

| Code                   | What it means                                                                                              | Raised by                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `INSUFFICIENT_FUNDS`   | The account can't cover the amount the request needs.                                                      | <ApiLink to="variables/economy-lab.spend" />, <ApiLink to="variables/economy-lab.subscribe" />, <ApiLink to="variables/economy-lab.requestPayout" />                                                    |
| `FUNDS_IMMATURE`       | The funds exist but are still in their holding period, so they aren't usable yet.                          | <ApiLink to="variables/economy-lab.spend" />, <ApiLink to="variables/economy-lab.subscribe" />, <ApiLink to="variables/economy-lab.requestPayout" /> (renewals defer on it)                             |
| `RISK_DENIED`          | The [velocity / abuse check](/economy/concepts/spend-velocity/) declined this request.                     | <ApiLink to="variables/economy-lab.spend" />, <ApiLink to="variables/economy-lab.subscribe" />, <ApiLink to="variables/economy-lab.topUp" />, <ApiLink to="variables/economy-lab.grantPromo" />, <ApiLink to="variables/economy-lab.requestPayout" /> (every risk-screened write) |
| `DUPLICATE_ORDER`      | A `spend` reused an `orderId` that already has a completed sale, but carried a different `idempotencyKey`. | <ApiLink to="variables/economy-lab.spend" />                                                                                  |
| `UNKNOWN_ORDER`        | No sale was found for the `orderId` the request refers to.                                                 | <ApiLink to="variables/economy-lab.refund" />                                                                                 |
| `NOT_ENTITLED`         | The user doesn't own the item or feature the request needs.                                                | <ApiLink to="variables/economy-lab.revokeEntitlement" />                                                                      |
| `UNKNOWN_SUBSCRIPTION` | No subscription matched the request.                                                                       | <ApiLink to="variables/economy-lab.cancelSubscription" />                                                                     |
| `ALREADY_SUBSCRIBED`   | The user already has an active subscription to this `sku` / seller; a second would double-bill.            | <ApiLink to="variables/economy-lab.subscribe" />                                                                              |
| `BELOW_MINIMUM`        | A payout was requested for less than the configured minimum.                                               | <ApiLink to="variables/economy-lab.requestPayout" />                                                                          |
| `PAYOUT_TOO_SOON`      | A payout was requested before the configured minimum gap since the user's last request.                    | <ApiLink to="variables/economy-lab.requestPayout" />                                                                          |
| `PAYEE_UNVERIFIED`     | The configured payee directory hasn't cleared the seller's identity verification.                          | <ApiLink to="variables/economy-lab.requestPayout" />                                                                          |
| `ECONOMY_PAUSED`       | A maintenance window is in effect, so an end user's discretionary write is declined.                       | Any paused user write                                                                    |
| `CATALOG_MISMATCH`     | The spend disagrees with the host catalog's live offer; `detail.field` names the disagreeing fact (`sku`, `price`, or `recipients`). | <ApiLink to="variables/economy-lab.spend" /> with a [catalog port](/economy/ports/catalog/) in the ports bag |

A few of these reward a closer look.

`FUNDS_IMMATURE` is a timing problem. The money is there, but it hasn't cleared its
maturity window yet. That concept lives with [credit maturity](/economy/concepts/credit-maturity/).
The `detail` names the `source` whose window is still open and `availableAt`, the time when the
funds will have cleared assuming no further activity. A caller can use `availableAt` to tell the
user when to try again.

`RISK_DENIED` names its trigger the same way. Its `detail` carries `window`, which names the
window that tripped: `'inflow'` for top-ups and promo grants, `'outflow'` for spends,
subscriptions, and payout requests. It also carries `limitMinor`, the ceiling of that
[velocity window](/economy/concepts/spend-velocity/).

`DUPLICATE_ORDER` catches a specific client mistake: a retried `spend` that lost its original
`idempotencyKey`. The `orderId` identifies a unique purchase. A second charge for the same order
is therefore a declined "no" rather than a thrown fault.

`ECONOMY_PAUSED` only ever stops end-user writes. A `system` actor's settlement and an `operator`'s
manual fix are never paused. The rules on [actors and authorization](/economy/concepts/actors-and-authorization/) define that split.
The decline carries `resumesAt` in its `detail`. The caller can use it to tell the user when to come back.

<Callout type="note">
  `ECONOMY_PAUSED` is a decline you can see coming. The `read.status()` reader
  exposes the live pause state directly. A UI can show a maintenance banner
  without first submitting a write and reading the rejection back. See the [read
  surface](/economy/reference/reads/).
</Callout>

`CATALOG_MISMATCH` is the decline that answers a caller's own price. When the economy is built
with a [catalog port](/economy/ports/catalog/), every `spend` is checked
against the host's live offer before it runs, whichever door it arrived through. The `detail`
carries the `sku` and the first disagreeing `field` — `sku`, `price`, or `recipients`. Without
the port, the same spend passes through unchecked.

## Rejected versus thrown

A `rejected` outcome is the economy's considered
"no" to a question it understood. A thrown fault means the question itself was broken.

They never overlap. The core decides up front which path a problem takes. A given failure
arrives either as a `RejectionCode` in the outcome or as a thrown exception, never as both.

Thrown faults carry their own codes. <ApiLink to="variables/economy-lab.ERROR_CODES" /> keeps them separate from the
rejection codes. You'll meet these six when a request is malformed or misdirected:

| Thrown code               | Constant              | When it's thrown                                                                                         |
| ------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------- |
| `OP.MALFORMED`            | `MALFORMED_OPERATION` | The request was structurally wrong: a missing or invalid field, or a `topUp` amount outside the configured [purchase catalog](/economy/reference/operations/top-up/). |
| `MONEY.INVALID_AMOUNT`    | `INVALID_AMOUNT`      | A money amount was invalid, such as negative or not a whole minor unit.                                  |
| `AUTH.UNAUTHORIZED`       | `UNAUTHORIZED`        | The actor isn't permitted to perform this action.                                                        |
| `SAGA.INVALID_TRANSITION` | `INVALID_TRANSITION`  | A [saga](/economy/concepts/payout-saga/) was told to move to a state it can't reach from its current one. |
| `SESSION.SETTLED`         | `SESSION_SETTLED`     | A settled [netting session](/economy/concepts/session-netting/) refuses further movements; rotate to a new session id (epoch). |
| `SESSION.MISROUTED`       | `SESSION_MISROUTED`   | A scope's traffic reached a [cluster node](/economy/concepts/cluster/) that doesn't own it; `detail.owner` names the node that does. |

The line between the two follows cause rather than severity. `INSUFFICIENT_FUNDS` is a healthy system
giving an expected answer. You show that rejection to the user. `INVALID_AMOUNT` means the caller sent a
number that can't be money. That is a fault to fix in code.

That separation has a practical payoff. Ordinary "no" answers stay off the thrown-error path.
They never light up error dashboards or page an on-call engineer.

<Callout type="warning">
  Don't reach for a `try`/`catch` to handle an empty balance or a duplicate
  order. Those come back as `rejected` outcomes. A `catch` will never see
  them. Branch on `result.status` instead. Keep `catch` for the genuine
  faults.
</Callout>

`ERROR_CODES` also holds deeper safety faults you won't normally trigger from a well-formed request:
`LEDGER.OVERDRAFT`, `CHAIN.BROKEN`, `LEDGER.COMMINGLING`, and others. Those are last-resort
backstops deep in the posting and integrity paths. Reaching one means an invariant was about to
break.

## Troubleshooting

### I get `duplicate` but I only submitted once

The key was minted from something two different actions share, such as a user id, a SKU, or a template string that never varies. The first action claimed it. Every later action replays that recorded outcome. Mint the key from the action's own identity:

```ts
const idempotencyKey = `ord_${order.id}`; // unique per order, stable per retry
```

[Idempotency & retries](/economy/concepts/idempotency/) owns the key discipline.

### My code throws instead of getting a `rejected` outcome

Then it wasn't a decline. The request itself was broken before any business question was asked. Two causes are the usual suspects: the `actor` is a `user` acting on an account they don't own (`AUTH.UNAUTHORIZED`), or the payload is malformed (`OP.MALFORMED`, e.g. a blank key). Rejections are reserved for valid requests the economy declines. See [rejected versus thrown](#rejected-versus-thrown) above and [actors & authorization](/economy/concepts/actors-and-authorization/).
