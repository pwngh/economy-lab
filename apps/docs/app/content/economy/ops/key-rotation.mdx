The checkpoint signer derives its Ed25519 key from `SIGNING_SECRET`. Checkpoints sealed under
an old secret must keep verifying forever, because the chain of custody is only as good as
the oldest verifiable seal. Rotation is therefore a two-variable move, never a replacement.

**Never rotate by replacing `SIGNING_SECRET` alone.** That silently breaks verification of
every checkpoint sealed before the change. The next `checkpointVerify` sweep reports a
mismatch, and you will be running the
[integrity-mismatch runbook](/economy/ops/runbooks/integrity-mismatch/) against your own key
change.

## The procedure

1. Generate the new secret. Any high-entropy string works, because the secret is hashed to
   the key seed.
2. Deploy with both variables set:

   ```bash
   SIGNING_SECRET=<new secret>
   SIGNING_SECRETS_PRIOR=<old secret>
   ```

   `SIGNING_SECRETS_PRIOR` is comma-separated. A second rotation makes it `<old>,<older>`.
   Each entry goes through the same derivation as `SIGNING_SECRET`, and <ApiLink to="interfaces/ports.Signer">Signer.verify</ApiLink> tries
   the current key first, then each prior in order.

3. Confirm continuity. The next scheduled sweep's `worker.checkpoint.verify` beat must report
   `outcome: 'ok'`. An `ok` outcome means the old checkpoint verified under a prior key.
4. Confirm succession. After the next seal, the newest checkpoint is signed under the new key
   and verifies without the prior list. `make prove` checks this on demand.
5. Keep a prior secret listed for as long as any checkpoint signed under it must verify.
   Keep it until every pre-rotation checkpoint has been superseded and until any external
   audit that pinned `signingPublicKeyHex` for the old key has re-anchored. Drop an entry
   only when you mean to expire that era's seals.

## If verification breaks after a rotation

The near-certain cause is a dropped or mistyped prior secret. Restore the exact old value
into `SIGNING_SECRETS_PRIOR`. Re-check the verify beat before you suspect tampering. Do not
skip the check. A mismatch that survives a corrected prior list is a real
[integrity-mismatch](/economy/ops/runbooks/integrity-mismatch/).

## Scope

The same secret also signs entitlement-gated URLs. Those URLs are short-lived, so rotation
only invalidates in-flight links. `WEBHOOK_SECRET` rotation is a separate, provider-coordinated
procedure. See [webhook-replay-storm](/economy/ops/runbooks/webhook-replay-storm/) for when
that rotation becomes urgent.
