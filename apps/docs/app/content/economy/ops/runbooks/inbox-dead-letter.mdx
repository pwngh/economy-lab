This is a [Tier 1](/economy/ops/the-supervisor/) signature with an automatic revive. Inbound provider events exhausted their
apply attempts and dead-lettered. Money that should have arrived (a top-up, a settlement) has
not.

## Symptoms

`worker.inbox.dead_lettered` error logs appear. Users report missing credits after
provider-confirmed payments.

## Detection

The detector counts each `worker.inbox.dead_lettered` log signal past a watermark, against
`inboxDeadLetterThreshold` (default 1). The signal buffer keeps event names only, never
fields, so the dead rows' ids are not visible to the detector — the store finds them itself.

## Automatic response

The supervisor runs `detected` → `decided` → `InboxStore.reviveDead`. The revive flips up to
`inboxReviveLimit` (default 10) oldest dead rows back to pending with attempts reset, then the
supervisor emits `acted` (the revived ids) and `verified`. The scheduled `drainInbox` picks
the rows up on its next sweep. The revive itself never applies anything. The money still moves
only through the normal drain under the row's idempotency key (`whk:<eventId>`). A wrong
revive costs work, not money. Four guardrails apply: episode cooldown, an attempt cap into
permanent escalation, containment suppression, and a `no-lever` decision when the host wired
no revive lever. A poison row that keeps dead-lettering opens a new episode each time, and the
attempt cap bounds it.

## Manual steps

1. Inspect before assuming transient:
   `select id, attempts, dead_letter_reason, received_at from inbox where status = 'dead' order by received_at;`
2. Read the `dead_letter_reason` on each row — it is the submit's error code, and it tells
   you whether a revive can ever work. `CONFIG.INVALID` / `OP.MALFORMED` mean the
   event decodes to an operation the economy rejects: replaying it will never succeed, so fix
   the mapping or resolve with the provider instead. Transient store codes revive freely.
   `WORKER.ATTEMPTS_ABANDONED` is not a submit code at all: no apply ever returned one, because
   the event took the worker process down every time. Reviving it repeats that, so find out what
   the apply does to the process first.
3. Revive the rows by hand when the supervisor is not doing it — run
   `store.inbox.reviveDead(limit)` from a host shell, then let the worker drain them on its
   next sweep.
4. After an escalation, resolve each row deliberately: fix-and-revive, or leave dead and
   settle with the provider out of band.

## Escalation

The attempt cap escalates with "poisoned, not delayed" attached. From there it is a data
conversation: what does the event contain, and why does the economy refuse it?
