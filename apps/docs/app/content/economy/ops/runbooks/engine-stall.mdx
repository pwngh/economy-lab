This is a [Tier 3](/economy/ops/the-supervisor/) signature, report-only. Connection acquires started and none completed.
Either the pool is starved or the database is unresponsive. Submits queue rather than fail —
nothing errors on its own.

## Symptoms

Latency climbs toward timeouts with no error spike. `engine.pool.acquire` counts keep arriving
with no matching `engine.pool.acquire_ms` completions.

## Detection

The detector looks for acquire starts (`engine.pool.acquire`) newer than the last completion
(`engine.pool.acquire_ms`). A finding fires when the oldest pending start is older than
`stallGraceMs` (default 10s). The rule reads the whole signal buffer, not a sliding window. A
stall emits nothing new to slide over.

## Automatic response

The supervisor emits `detected` + `escalated` once per episode. The episode resets when a
completion arrives, so a recovered-then-stalled pool escalates fresh. The pass runs before the saga poll so a hung
store cannot block the audit trail.

## Manual steps

1. Check the database is reachable at all — connect by hand with `psql` or `mysql`. If you
   cannot connect, this is an infrastructure outage, not an engine stall.
2. Inspect the pool size next — `DB_POOL_MAX` (default 10 per driver). A known failure mode
   is pool starvation from transactions needing a second connection mid-flight; it looks
   exactly like this signature, so a small pool with chaining transactions points at
   starvation rather than a dead database.
3. Check for long-running transactions holding connections — run the query for your engine.
   Any row with an old start time is a connection that will not return to the pool until it
   finishes or is killed:
   - Postgres: `select pid, state, query_start, query from pg_stat_activity where state <> 'idle' order by query_start;`
   - MySQL: `SHOW PROCESSLIST;`

## Escalation

If the database is up and the pool is sized sanely, escalate to whoever owns the database
host. A stall with healthy config is an infrastructure problem.
