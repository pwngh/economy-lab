This is a [Tier 1](/economy/ops/the-supervisor/) signature, the one classic automatic remediation. A payout saga sits in a
non-terminal state with nothing advancing it. The usual cause is a background worker that is
down or a schedule that stopped.

## Symptoms

A seller's payout stays "requested" past the SLA. `worker.payouts.saga_age_ms` grows.
`worker.sweep` heartbeats may be missing entirely (see
[signal-silence](/economy/ops/runbooks/signal-silence/)).

## Detection

The supervisor polls `SagaStore.list()` each tick. Any saga in a non-terminal state (not
`SETTLED`/`FAILED`) older than `stuckSagaAgeMs` (default 5m, by `updatedAt`) is a finding, one
per saga id.

## Automatic response

For each stuck saga, the supervisor runs `detected` → `decided` → one worker sweep
(`runSweep`, the host's `worker.sweep` closure) → `verified` by re-reading the saga
(`progressed` when its state or `updatedAt` moved). Three guardrails apply, all mandatory:

- cooldown `actionCooldownMs` (default 60s) between actions per saga;
- attempt cap `maxActionAttempts` (default 3), then a permanent `escalated` record — the
  supervisor never touches that saga again;
- suppression under [containment](/economy/ops/runbooks/integrity-mismatch/) — a mismatch
  episode outranks a stuck payout.

One sweep serves every actionable saga; there is no per-saga targeting.

## Manual steps

1. Read the audit trail for the saga id and confirm two things: that the sweep actually ran,
   and whether `verified` came back `unchanged`. An `unchanged` verdict after a real sweep
   means the sweep is not what is holding the saga up — look past the worker.
2. Run `make worker` (or check the deployment) to confirm the worker is alive — the usual
   root cause here is the worker process, not the saga itself.
3. If the saga keeps surviving sweeps, treat it as wedged on its provider step. Check the
   payout provider's status for the saga's `providerRef`, and read the `worker.payouts.*`
   logs (`status_probe_failed`, `pending_past_timeout`).
4. Reproduce the whole closed loop in-memory with `make demo-ops` if you need to see the
   remediation path end to end.

## Escalation

The attempt cap escalates on its own. From there it is a provider conversation or a
dead-letter decision (`SagaStore.deadLetter`) — never an automatic one.
