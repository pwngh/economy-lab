This is a [Tier 3](/economy/ops/the-supervisor/) signature, report-only. Merkle sealing is trending slower — a
table-growth problem brewing, caught while it is still a trend.

## Symptoms

None yet. This signature fires on a trend, before any outage. `worker.checkpoint.seal_ms` observations
tagged `outcome: 'sealed'` climb across days.

## Detection

The detector takes the max `worker.checkpoint.seal_ms` tagged `outcome: 'sealed'` over
`sealLatencyWindowMs` (default 5m). A max at or past `sealLatencyMs` (default 5s) is a finding.
Only completed seals count. A skip or retry says nothing about re-derivation cost.

## Automatic response

The supervisor emits `detected` plus a `decided` advisory once per window. No remediation
exists on purpose: the seal is the worker's only scheduled full-chain re-derivation, a
signing-path security property rather than a cost to flatten automatically.

## Manual steps

1. Confirm it is growth, not a blip: plot `seal_ms` against `chain_links` row count
   (`select count(*) from chain_links;`). Linear tracking is the expected cost curve;
   super-linear points at a query plan or index problem in the store's `heads()` path.
2. Check the seal is not competing for the connection pool with live traffic — watch for
   [engine-stall](/economy/ops/runbooks/engine-stall/) symptoms during the sweep window. If
   they coincide, the slowdown is contention, not re-derivation cost.
3. Capacity-plan while calm: the levers are the sweep interval (`WORKER_INTERVAL_MS`),
   database sizing, and — as a design decision, not an ops action —
   [platform sharding](/economy/concepts/platform-sharding/). An incremental seal is a
   signing-path change and needs a security review, not a config tweak.

## Escalation

Escalate to the ledger owner as a planning item, with the trend data. If this signature pages
anyone at 3am, the thresholds are set wrong.
