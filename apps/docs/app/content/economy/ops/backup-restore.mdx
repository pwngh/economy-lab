A backup that isn't provably restorable is a hope, not a backup. The lab ships both halves.
`make backup` dumps the data. `make restore-drill` proves the dump restores. The drill
restores into a scratch namespace, runs the full prover against it, and drops the scratch
afterward.

## Backup

`make backup` writes a data-only dump per env-named engine into `backups/`:

- postgres: `pg_dump --data-only --no-owner --schema=public --disable-triggers` →
  `backups/pg-<stamp>.sql`
- mysql: `mysqldump --no-create-info --single-transaction --replace --skip-triggers` with the
  table list parsed from `packages/mysql/db/mysql-schema.sql` → `backups/mysql-<stamp>.sql`. The parsed
  table list keeps the unrelated tables of a shared database out of the dump.

The dump skips DDL on purpose: the drill applies each engine package's canonical schema
(`packages/postgres/db/postgresql-schema.sql`, `packages/mysql/db/mysql-schema.sql`) at restore
time, which also proves the dump still matches the current schema (`schema_meta` rides in the
data). The trigger bypass is safe because nothing is trusted to it — the prover re-checks
every invariant the triggers enforce. If an engine the env names fails to dump, the whole run
fails rather than produce a backup that silently skips an engine.

## The drill

`make restore-drill` takes the newest dump per engine and closes the loop:

1. Create a scratch `el_drill_*` database.
2. Apply the engine's schema file. Then clear the seeded platform rows (postgres; the mysql dump uses
   `REPLACE`). Clearing the seeds means the dump's values land, not the seeds.
3. Apply the dump. Open a real store on the scratch. Run the full prover: `conserved`,
   `backed`, `noOverdraft`, `chainIntact`, `consistent`. PASS requires every check true.
4. Drop the scratch in a `finally`. A killed drill leaves an `el_drill_*` name that
   `make db-clean` sweeps.

Run the drill after every backup-tooling or schema change, and run it on a schedule. A drill
that has not run since the schema last changed proves nothing.

## A real restore

The drill is the rehearsal. A disaster restore is the same moves against a fresh production
database, minus the drop:

1. Stop the worker and the API. Stopping them ensures nothing writes during the restore.
2. Create the database. Apply the engine's schema file. Clear the seeded rows.
3. Apply the chosen dump. Point `DATABASE_URL` at the new database.
4. Run `make prove` before taking traffic. Then restart and watch the first
   `worker.checkpoint.verify` beat.

The backup contains the sealed checkpoints, and the prover re-derives the chain against them.
A restore is therefore only as trustworthy as the custody of the dump. That is why you ship
dumps and the [audit trail](/economy/ops/audit-trail/) to write-once storage. Losing the tail
between the last dump and the incident is expected. The chain makes the cut point provable,
not invisible.
